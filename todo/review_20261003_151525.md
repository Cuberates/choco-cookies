# Review of todo2.md

I reviewed [todo/todo2.md](./todo/todo2.md) under the assumption that bowwwl.com is stable and never changes structure. In that scenario, the plan is mostly sound and the “live scrape” concern becomes much less severe.

## Summary

- The main idea is good for a personal project.
- A one-off catalog import into PostgreSQL is a reasonable approach.
- Explicit on-demand import is better than scraping on startup.
- A database-backed catalog is a strong fit for search/filtering and pagination.

## Items to tighten before implementation

### 1. Keep the import as a deliberate admin task

The import should remain a manual or admin-triggered process, not something that runs during normal app startup. This keeps the application predictable, avoids unnecessary scraping, and makes failures easier to diagnose.

### 2. Define a stable identity for each ball

The plan should explicitly state the canonical identity of each imported ball. A robust approach is to use a deterministic source key such as:

- source URL
- source ID
- or a normalized combination of both

This is necessary so reruns can update existing records without creating duplicates.

### 3. Clarify the weight model before finalizing the schema

The plan should specify whether ball weight is:

- a single numeric value
- a range
- or multiple values per item

This affects both the JPA model and the filter UI.

### 4. Define behavior for unknown values

The implementation should decide how missing values are handled, such as:

- null values
- "Unknown" strings
- or excluding those fields from filterable metadata

This keeps data quality consistent without dropping usable records.

### 5. Add explicit import result accounting

The plan should report counts for:

- imported records
- updated records
- skipped records
- malformed records

That gives a clear operational view of the catalog sync process.

### 6. Keep the DB configuration fail-fast and secure

Even in a personal project, the database settings should be validated strongly and startup should fail clearly when required configuration is missing or invalid. That includes:

- using environment variables
- keeping secrets out of version control
- documenting local vs. deployment configuration clearly

### 7. Add fixture-based testing discipline

The intention to use saved sample HTML is good. The implementation should ensure tests never hit the live site and instead use version-controlled fixtures for parser and repository validation.

## Overall verdict

As a personal project, this is a solid plan. The only important caution is not that the site may change, but that the import must be idempotent, predictable, and safe when data is incomplete. The plan is very viable under the stated assumption.
